# Фаза 7. Интеграция: конфиг, Alt-Svc, метрики, лимиты, перезагрузка

К этому моменту h3 работает, но им никто не пользуется: браузер о нём не знает,
оператор не может его настроить и не видит, что происходит. Эта фаза делает h3
пригодным для эксплуатации.

---

## 1. Конфигурация

### 1.1 Секция vhost

```json
"servers": {
  "s1": {
    "domains": ["www.example1.com"],
    "ip": "0.0.0.0",
    "port": 443,
    "tls": { "fullchain": "...", "private": "...", "ciphers": "..." },
    "http3": {
      "enabled": true,
      "port": 443,
      "alt_svc": true,
      "alt_svc_max_age": 86400
    },
    "http": { "...": "..." }
  }
}
```

- `port` по умолчанию равен TCP-порту vhost. Разные порты допустимы, но тогда
  `Alt-Svc` обязан их указывать.
- Эндпоинт создаётся на каждую уникальную пару (ip, udp-порт) — так же, как
  `__listener_get()` объединяет vhost'ы на один TCP-listener. Выбор vhost внутри
  соединения — по SNI, точно как в TCP+TLS.
- `enabled: true` без секции TLS — ошибка конфигурации: QUIC без TLS не бывает.

### 1.2 Параметры `main.env`

По образцу `h2_policy_init()` — плоские ключи, читаются один раз в
`module_loader` до старта потоков, лежат в глобалах. Добавляется
`h3_policy_init()`, вызываемая там же, где `h2_policy_init()`.

Для rate/budget-настроек `0` по-прежнему означает «выключено» там, где это
указано явно. `http3_max_connections` — исключение: `0` и значения вне
`64..4000000` являются ошибкой конфигурации, а не скрытым clamp.
Для `http3_buffer_memory_limit` значение `0` явно отключает байтовый лимит и
пишет предупреждение; отсутствие ключа означает 25% физической RAM.

## 2. Alt-Svc — иначе h3 никто не увидит

Браузер не пробует UDP наугад. Он узнаёт о h3 одним из двух способов:

1. **Заголовок `Alt-Svc`** в ответе по h1.1/h2:
   ```
   Alt-Svc: h3=":443"; ma=86400
   ```
2. **DNS HTTPS/SVCB RR** (RFC 9460) — вне зоны ответственности сервера, но
   документируем в `frontend/docs`:
   ```
   example.com. 3600 IN HTTPS 1 . alpn="h3,h2" port=443
   ```

**Реализация.** Заголовок добавляется в `http_write_filter` и `h2_write_filter`
(не в h3 — там он бессмысленен) для vhost'ов с `http3.alt_svc: true`. Место —
рядом с добавлением `Date`/`Server`; одна строка, значение вычисляется один раз
при загрузке конфига и хранится в `server_t`.

Не добавлять на ответы 1xx и на ответы, где заголовок уже задан хендлером.

**Замечание к решению по h2.** В `docs/http2/08` фаза F.2 кадры `ALTSVC`/`ORIGIN`
были закрыты по решению «не нужно». Это не противоречит: там речь о кадре
`ALTSVC` (0xa) протокола HTTP/2, а здесь — о заголовке `Alt-Svc` (RFC 7838),
который несёт обычный HTTP-ответ. Для обнаружения h3 нужен именно заголовок.

### 2a. Ход работ

**Сделано.** Ключи `http3.alt_svc` (по умолчанию **включён**, если включён сам
h3) и `http3.alt_svc_max_age` (86400). Значение собирается один раз при загрузке
конфига в `server_http3_t::alt_svc_value` — оно не может измениться на работающем
сервере, а `snprintf` на каждый ответ был бы на самом горячем пути, какой есть.

Заголовок ставит общий `httpfields_apply_alt_svc()`, вызываемый из
`http_write_filter` и `h2_write_filter` **до** сериализации головы: после неё
поля — уже байты. Из h3-фильтра не вызывается: сказать клиенту по HTTP/3, что
доступен HTTP/3, — не сообщение.

Три правила, каждое проверено:

- **1xx пропускается.** Промежуточный ответ не финальный, его поля клиент вправе
  выбросить, а финальный их повторит;
- **свой заголовок хендлера побеждает** — хендлер, назвавший альтернативу, знает
  то, чего не знает конфиг;
- **повторный вызов не удваивает заголовок.** Это не гипотетика: стадия
  заголовков в фильтре выполняется на каждом ходе, и ответ, возобновлённый после
  `CWF_EVENT_AGAIN`, проходит здесь снова.

В значении указан **только порт, без хоста**: пустой хост в RFC 7838 означает
«тот же самый», и это оставляет заголовок верным для всех vhost'ов, делящих
листенер, не привязывая клиента к имени, которого может не быть в сертификате.

Проверено на живом сервере: `Alt-Svc: h3=":18443"; ma=86400` приходит по h1.1 и
по h2, по h3 — нет. +9 проверок в `test_altsvc.c`.

**Осталось по §2:** запись DNS HTTPS/SVCB — она вне сервера, но должна попасть в
`frontend/docs`.

### 1.2a. Ход работ

**Сделано:** `h3_policy_init()` — вызывается из `module_loader` рядом с
`h2_policy_init()`, с тем же контрактом: читает env один раз до появления
воркеров, дальше глобалы только читаются. Пока реализованы ключи прикладного
слоя (транспортные из таблицы выше — вместе с настройкой `quicconn`):

```
http3_max_field_section_size   1048576
http3_abort_rate / _burst      100 / 200
http3_ctrl_rate  / _burst      100 / 200
```

Первый закрывает костыль: до него h3 объявлял `MAX_FIELD_SECTION_SIZE` из
`http2_max_header_list_size`. Это тот же бюджет по той же причине, но два
протокола на одном операторском ключе означают, что ни один нельзя настроить, не
трогая другой.

**Транспортные ключи готовы (2026-08-09).** Параметры соединения перестали быть
константами внутри `quicconn_accept`:

```
http3_idle_timeout_sec         30      [1 .. 3600]
http3_max_udp_payload_size     1350    [1200 .. QUIC_DEFAULT_UDP_PAYLOAD]
http3_initial_max_data         1048576 [1200 .. 1 ГиБ]
http3_initial_max_stream_data  262144  [1200 .. 1 ГиБ]
http3_max_streams_bidi         100     [1 .. 65536]
http3_max_streams_uni          8       [3 .. 65536]
http3_recv_window_max          16 МиБ  [initial_max_data .. 1 ГиБ]
http3_active_cid_limit         4       [2 .. 8]
http3_ack_delay_ms             25      [0 .. 16383]
http3_initcwnd_packets         10      [2 .. 64] датаграмм, RFC 9002 §7.2
http3_pacing                   true
http3_amplification_factor     3       [1 .. 16]

http3_handshake_rate           500     новых рукопожатий/с, 0 = без лимита
http3_handshake_burst          1000
```

Границы — не вкусовые: `max_streams_uni` не может быть меньше **трёх**, потому
что до первого ответа HTTP/3 нужны control и оба QPACK-потока; ceiling у
`max_udp_payload_size` — размер пакетного буфера, в который строит `quicconn`
(объявить больше — пообещать место, которого нет); `ack_delay_ms` ограничен
14 битами поля §18.2; `recv_window_max` не может быть ниже `initial_max_data`,
иначе окно умеет только уменьшаться. Отклонение `amplification_factor` от 3
пишется в лог прямым текстом — это не настройка, а способ уронить лимит в тесте.
`initcwnd_packets` — тот же выбор, что у TCP `initcwnd`: RFC рекомендует 10
датаграмм, но на длинном RTT (спутник, трансокеанский путь) файл в 30 КБ при
десяти пакетах едет два RTT только на разгоне окна. Отклонение от 10 тоже
пишется в лог; потолок 64 — где перестаёт быть настройкой и становится
burst'ом в сторону пути.

`http3_pacing` (§7.7) долгое время был ровно тем ключом, который «ничего не
меняет»: `quicpacer_*` существовал, но не вызывался ниоткуда, кроме своего же
файла — отправку ограничивал один `quiccc_available()`. Подключён 2026-08-15.
Бюджет всплеска — **начальное окно**, а не десять датаграмм: §7.2 определяет
initial window как ровно тот burst, которым сендер вправе открыть путь, а §7.7
не советует burst'ы крупнее и дальше. Отсюда три следствия: стартовый флайт
уходит так же, как без пейсера вовсе (регрессии на коротких ответах нет);
оператор, поднявший `initcwnd_packets`, получает заказанный burst целиком;
всё, что окно освобождает потом — а один кумулятивный ACK освобождает окно во
много раз больше начального, — размазывается, а не вываливается. Что пейсер
никогда не задерживает: ACK (не в полёте — значит, не под контролем
перегрузки) и PTO-пробу (§7.7 разрешает её без оглядки на pacing, по той же
причине, по которой §7.5 разрешает ей превысить окно). Оба исключения
достались даром — `pace_blocked` сворачивается в тот же `cc_blocked`, который
`__build_packet` уже умеет обходить для этих двух случаев.

Дедлайн, а не ожидание ACK: окно открывается, когда пир что-то скажет, а
бюджет пейсера — только по часам. Поэтому ход, который пейсер остановил,
оставляет `conn->pace_until_us`, его отдаёт `quicconn_next_timeout`, и
`want_write` остаётся поднятым, чтобы разбуженный ход нашёл работу. Деление при
расчёте дедлайна — **с округлением вверх**: пополнение (`rate * elapsed /
1e6`) усекает, и дедлайн, округлённый вниз, возвращал меньше датаграммы —
сендер просыпался всё ещё запертым и просил тот же миг снова. Стенд поймал это
как передачу, вставшую за 208 байт до конца, пока часы ползли по микросекунде
за ход.

**Где они живут и почему.** По смыслу это transport parameters, то есть епархия
`quicconn`. Но читаются они из `main.env`, и чтение env из транспортного слоя
затащило бы зависимость от конфига под каждый юнит-тест, который строит
соединение. Поэтому они читаются в уже существующей `quic_policy_init()`
(`src/udp/quicendpoint.c`) — единственной функции, которая делает ровно это и в
нужный момент, — а `quicconn_accept` берёт готовое через
`quic_policy_conn()`. Значения копируются **на accept** и больше не
перечитываются: они уже объявлены пиру, и reload не вправе поменять арифметику
живого соединения.

`http3_cc` (альтернативы NewReno нет), `http3_tx_batch` (`sendmmsg` не
используется — §01 объясняет, почему у батчинга отправки нет пользователя),
`http3_qlog_*` (qlog — заглушка) и ключи Retry/токенов не заведены: ключ, который
ничего не меняет, хуже отсутствующего.

Проверено вживую: `quicclient` печатает все параметры сервера (это единственное
место, где их видно — они едут внутри зашифрованного рукопожатия). Прогон с
нестандартными значениями показал их на проводе один в один, прогон с
заведомо выходящими за границы — обрезанными по таблице выше, и запрос при этом
всё равно проходит. +12 проверок в `test_quic_policy.c` — на инварианты
дефолтов, а не на границы: границы утверждает та же таблица, что их задаёт,
а дефолты нужны каждому юнит-тесту, который строит соединение без конфига.

## 3. Метрики

Расширение `/metrics` (секции появляются, только если h3 включён).

```
quic.*            — из фазы 1 (§9 документа 01)
quic.handshakes_started / completed / failed{reason=tls|timeout|refused}
quic.retry_sent, quic.token_valid, quic.token_invalid{expired|addr|forged}
quic.rtt_us{p50,p90,p99}, quic.cwnd_bytes{p50,p99}
quic.packets_lost, quic.loss_rate, quic.pto_fired, quic.persistent_congestion
quic.key_updates, quic.decrypt_failures
quic.migrations{attempted,validated,rejected}
quic.streams_open, quic.streams_reset
quic.flow_blocked{conn,stream}
quic.amplification_limited     — сколько раз упёрлись в 3x

http3.requests, http3.responses{1xx,2xx,3xx,4xx,5xx}
http3.streams_cancelled, http3.goaway_sent
http3.abuse{abort_budget,ctrl_budget,field_section_too_large,blocked_streams}
http3.qpack{inserts,evictions,blocked_streams,literal_ratio}
```

Плюс новые `LOCK_SITE_*` из `01` §3.6, попадающие в существующую гистограмму
ожидания `connection_s_lock` — тот же инструмент, что уже нашёл лишний лок в h2
(`docs/concurrency/01` §6, A.4).

### 3a. Ход работ

**Сделано (2026-08-09).** Секции `quic` и `http3` в `/metrics` заполнены всем,
что сегодня существует в коде. Проверено вживую: `quicclient` против сервера с
`"metrics": true` — `handshakes_completed`, `streams_opened`, `requests`,
`responses.2xx`/`4xx` и обе гистограммы ненулевые. +54 проверки в
`test_h3metrics.c`.

Что добавилось к счётчикам фазы 1: исходы рукопожатия
(`handshakes_completed`, `handshakes_failed.tls`, `handshakes_failed.timeout`),
`decrypt_failures` и `aead_limit_reached`, восстановление (`packets_lost`,
`pto_fired`, `persistent_congestion`), причины, по которым отправка встала
(`flow_blocked.connection`, `flow_blocked.stream`, `amplification_limited`),
потоки (`streams_opened`, `streams_reset_sent`, `streams_reset_received`) и
разбор закрытий по причине (`closed.idle_timeout`, `closed.local_error`,
`closed.peer`). Секция `http3` — целиком по списку выше, кроме `qpack.*`.

Три решения, которые расходятся с таблицей и приняты сознательно:

- **`handshakes_started` не заведён.** Соединение создаётся первым Initial,
  который дошёл до `quicconn_accept`, — это ровно `connections_accepted` из
  фазы 1, и второй счётчик был бы вторым именем того же события.
- **Не p50/p90/p99, а гистограмма.** Точные квантили требуют хранить выборку, а
  хранить её — это либо предел, который молча срезает хвост, либо аллокация на
  пути ACK. Вопросы, которые этим числам задают («путь медленный?», «окно так и
  не выросло?»), отвечаются тем, в каком ведре лежит масса; ведро для `cwnd`
  начинается с начального окна (~12–15 КБ) именно поэтому. Минимум не
  публикуется: наименьший RTT по всем соединениям — это ближайший клиент, а не
  свойство сервера (per-connection `min_rtt` живёт в `quicloss`).
- **Счётчиков, которым неоткуда взяться, нет.** `retry_sent`, `token_*`,
  `key_updates`, `migrations.*` — код Retry и токенов есть в `quicretry.c`, но
  эндпоинт его пока не зовёт, а key update и миграция — фаза 9. Счётчик,
  который не может стать ненулевым, читается как «этого не происходит», а не
  как «этого не реализовано», — то есть врёт в самый неподходящий момент.

Асимметрия, которую стоит знать заранее: `requests` считается в момент, когда
секция полей превратилась в запрос (`H3STREAM_REQUEST_READY`). Исходы, которые
это событие **заменяют**, а не следуют за ним, — 431 по превышению секции полей
и malformed-запрос — считаются своими счётчиками. Значит при потоке 431-х сумма
`responses.*` может превысить `requests`: эти ответы не отвечали ни на какой
запрос.

`abuse.abort_budget` и `abuse.ctrl_budget` считаются внутри
`h3session_*_spend()`, а не в четырёх местах вызова: исчерпание — одно событие с
несколькими путями к нему.

Добавлено вместе с §4 (2026-08-09): `refused.at_capacity`,
`refused.handshake_rate`, `abuse.field_section_hard_cap`.

Добавлено 2026-08-15: `quic.connections.{current,limit,peak}` и
`quic.handshakes.inflight`. Это process-wide gauges; `peak` считается с запуска
процесса и не сбрасывается soft reload.

Там же добавлено `quic.memory.{current_bytes,limit_bytes,refused}`. Учитывается
реально выделенная capacity динамических stream receive/send и TLS CRYPTO
буферов, включая метаданные receive-сегментов. Резервирование выполняется до
`malloc/realloc`, а каждый error/consume/free path возвращает резерв.

**Осталось по §3:** `qpack.*` (придёт с full QPACK 6.2), `loss_rate` (частное,
которое считает читатель), и счётчики нереализованного из списка выше.

## 4. Защита от злоупотреблений

QUIC даёт атакующему возможности, которых не было в TCP. Каждая закрывается
бюджетом по образцу `docs/http2/08` фаза A (милли-токены, свой бакет на
семантику).

| Вектор | Защита |
|---|---|
| Спуфинг адреса → отражение | anti-amplification 3× (MUST) + Retry по порогу |
| Флуд Initial-пакетов | `http3_handshake_rate/burst`, отказ `CONNECTION_REFUSED` |
| Флуд пакетов с неизвестным CID | бюджет stateless reset; поиск по хеш-таблице O(1) |
| Rapid Reset (RESET_STREAM без ответа) | `http3_abort_*`, как в h2 |
| Флуд PING/ACK/NEW_CONNECTION_ID | `http3_ctrl_*` |
| Огромный список полей | `MAX_FIELD_SECTION_SIZE` + жёсткий предел ×2 → 431 |
| QPACK-бомба | предел декодированного размера, лимит блокированных потоков |
| Дыры в потоке (память на сегменты) | лимит `buffered` в `quicrecvbuf` → `FLOW_CONTROL_ERROR` |
| Открытие максимума потоков без данных | `initial_max_streams_bidi`, счётчик «пустых» потоков |
| Флуд NEW_CONNECTION_ID | `active_connection_id_limit`, превышение → `CONNECTION_ID_LIMIT_ERROR` |
| Миграция-флуд | не чаще одной валидации пути за 3×PTO |
| Огромный ACK-«гребёнка» | ≤ 32 диапазона на приём и на отправку |

Handshake, Version Negotiation и stateless-reset buckets являются процессными:
workers и endpoint не умножают настроенные rate/burst. Короткий atomic spinlock
защищает только обновление одного bucket и не попадает на data path
установленных соединений. Число незавершённых handshake также process-wide и
служит единым сигналом для `http3_retry=auto`.

### 4a. Ход работ

**Сделано (два бюджета прикладного слоя):** дырявые вёдра в милли-токенах — та
же форма, к которой пришла `docs/http2/08` фаза A, и по той же причине:
пополнение целочисленное и точное, остаток не теряется, сколько бы раз ни
вызывали.

- **`abort_*` — Rapid Reset.** Тратится, когда клиент присылает `RESET_STREAM`
  на поток, которому мы **ещё не ответили**; отмена после ответа — обычный
  клиент, передумавший, и она бесплатна. QUIC делает эту атаку **дешевле**, чем
  HTTP/2: между атакующим и следующим потоком нет рукопожатия, так что бюджет
  здесь нужнее, а не менее нужен, чем в h2;
- **`ctrl_*` — то, что заставляет работать, ничего не продвигая:** `GOAWAY` и
  `MAX_PUSH_ID`, повторяющие текущее значение (законно, два байта на отправку,
  ноль изменений); кадры неизвестного типа, которые мы пропускаем (§9 велит
  игнорировать *тип*, а не принимать неограниченный их поток); и каждый
  однонаправленный поток неизвестного типа — он стоит нам кадра `STOP_SENDING`
  и слота потока.

Два ведра, а не одно: частота отмен у честного клиента ничего общего не имеет с
частотой управляющих кадров, и одно ведро пришлось бы настраивать по более
слабому из двух. Исчерпание любого → `H3_EXCESSIVE_LOAD` на соединении. Вёдра
стартуют **полными**: всплеск на свежем соединении — это то, что делает
легитимный клиент, и пустой старт наказывал бы именно его.

+49 проверок в `test_h3budget.c` — каждый вектор проверяется с обеих сторон:
что бюджет кончается (и именно `H3_EXCESSIVE_LOAD`), и что обычный трафик до
него не доходит.

**Сделано (2026-08-09): жёсткий предел на секцию полей.** Пределов стало два, той
же формы, что в `docs/http2/08` фазе A:

- **объявленный** (`SETTINGS_MAX_FIELD_SECTION_SIZE`) проверяется по секции,
  которая **декодировалась целиком**, и это 431: сообщение корректно, и клиенту
  можно сказать, что с ним не так, — а сказать это нечем, если соединения уже
  нет;
- **жёсткий** уходит в сам декодер, который останавливается в тот момент, когда
  предел пройден. Блок такого размера декодируется ровно настолько, чтобы
  доказать, что он такого размера, и соединение закрывается: пир, приславший
  один такой, не пришлёт следующий поменьше.

Множитель — **×8, как в h2**, а не ×2 из таблицы выше. Оператор настраивает одну
идею «слишком много заголовков» на оба протокола, и два разных множителя за
одной идеей — ловушка; цифра h2 при этом выбиралась осознанно, а ×2 здесь была
догадкой на этапе плана. 0 («без предела») остаётся нулём: ноль, умноженный на
множитель, не должен превращаться в предел ноль.

До этого объявленный предел делал обе работы сразу, и на секцию полей любого
размера единственным исходом был ответ. +6 проверок в `test_h3stream.c` — обе
границы и полоса между ними. Попутно там нашлась ловушка самого теста: буфер
блока в хелпере `headers_frame` был 512 байт, а `qpack_encode_block` при нехватке
места возвращает 0 — тест «кормил» пустой HEADERS, полагая, что кормит огромный.

**Сделано (2026-08-09): бюджет частоты рукопожатий.** `http3_handshake_rate` /
`_burst` (по умолчанию 500/1000) — третье ведро эндпоинта, рядом с вёдрами
Version Negotiation и stateless reset. Рукопожатие — самое дорогое, что может
попросить неаутентифицированный пир: подпись, цепочка сертификатов на проводе и
состояние соединения, живущее до idle-таймаута. Ведро тратится **последним**,
после всех более дешёвых причин отбросить датаграмму: пакет, который и так не
открыл бы соединение, не должен съедать бюджет настоящих.

Отказ — **молчаливый дроп, а не `CONNECTION_REFUSED`**, вопреки таблице выше.
Отправить отказ значит вывести Initial-ключи и построить пакет на каждую
прилетевшую датаграмму — работа в пользу того, кто нас заливает, да ещё и на
непроверенный адрес. Ретрансмиссии честного клиента разбираются с остальным.
`CONNECTION_REFUSED` осмысленно на другом случае — сервер **полон**, а не
залит, — и требует построения Initial-пакета без соединения, то есть той же
машинерии, что и Retry (`quicretry.c` написан, но эндпоинт его не зовёт). Оба
должны приезжать одним шагом.

Счётчики отказов разведены: `refused.at_capacity` (упёрлись в
`http3_max_connections`) и `refused.handshake_rate` — это разные действия
оператора, и одно число не говорит ни о чём. Проверено вживую: при
`rate=1, burst=1` три подряд рукопожатия дают 2 принятых, 2 отказа по частоте.

**Осталось по §4:** лимит блокированных потоков (придёт с full QPACK 6.2),
счётчик «пустых» потоков и динамический `initial_max_data`.

Счётчик «пустых» потоков отложен осознанно: открыть поток в QUIC без данных
нельзя (поток появляется от кадра), число одновременных ограничено
`initial_max_streams_bidi`, а отмену уже ловит `abort_*`. Пока не видно вектора,
который эти три вещи не закрывают, — а счётчик без внятного порога лишь добавит
ещё одну цифру, на которую нечем ответить.

Отдельный пункт — **память на соединение**. Оценка потолка: recv-буферы
(`initial_max_data` = 1 МБ) + send-буферы + сегменты + ключи ≈ 1.3 МБ на
соединение в худшем случае. Даже при default
`http3_max_connections = 65536` теоретический потолок значительно выше
разумного RSS. Сейчас этот параметр является точным атомарным **процессным**
лимитом: слот резервируется до `quicconn_accept()` и освобождается при закрытии
или rollback. Дополнительно `http3_buffer_memory_limit` ограничивает общую
capacity динамических receive/send/CRYPTO-буферов. При исчерпании новые
соединения получают `CONNECTION_REFUSED`, а рост буфера активного соединения
завершается соответствующей transport/application error веткой.

## 5. Перезагрузка и остановка

Существующая модель: `appconfig->shutdown`, `reload: soft|hard`,
`__listeners_unlisten()`, дренаж по `api->connection_count`.

Для h3:

| Событие | Поведение |
|---|---|
| `shutdown` (мягкий) | Перестать принимать новые Initial (отвечать `CONNECTION_REFUSED`); по каждому соединению — h3 GOAWAY, дождаться потоков, `CONNECTION_CLOSE(H3_NO_ERROR)`; закрыть UDP-сокет, когда соединений не осталось |
| `reload: soft` | То же, но `endpoint->reset_key` и `token_key` **переносятся** в новую конфигурацию, иначе выданные NEW_TOKEN и stateless reset станут невалидными |
| `reload: hard` | Сокеты закрываются немедленно; клиенты переоткроют соединение (для QUIC это дешевле, чем для TCP, — 1-RTT) |
| SIGTERM с таймаутом | По истечении — `CONNECTION_CLOSE(NO_ERROR)` всем и выход |

Дренаж встраивается в `__mpx_on_tick` рядом с `h2_server_tick()`:
`quicendpoint_tick()` проходит по своим соединениям и применяет ту же политику.
Как и `h2_server_tick`, функция сама владеет жизненным циклом лока и может
освободить соединение — вызывающий обязан сохранить `next` заранее.

### 5a. Ход работ

**Сделано (2026-08-09): мягкая остановка.** До неё `shutdown_now` закрывал
активные соединения немедленно — то есть посреди запроса, — а перед этим
`quicendpoints_unlisten()` закрывал UDP-сокет.

**Главное отличие от TCP, ради которого пункт вообще нетривиален.** В TCP
закрытие listener'а останавливает новые соединения, а установленные живут
дальше: у каждого свой дескриптор. В QUIC **один сокет несёт и то и другое**,
поэтому «перестать принимать» не может быть «закрыть сокет» — закрытие бросило
бы ровно те соединения, которые дренаж и должен дообслужить. Поэтому теперь у
эндпоинта есть флаг `draining`, а сокет закрывается, когда ушло последнее
соединение. Это же и держит воркер живым: пока эндпоинт зарегистрирован,
`connection_count` не дойдёт до нуля, и цикл не выйдет раньше времени.

Дальше по образцу `h2_server_tick`: один раз h3 `GOAWAY` (идемпотентно —
повтор был бы тем самым флудом управляющих кадров, против которого стоит бюджет
из §4), затем ожидание, пока не закончатся **запросы**, а не потоки: счётчик
потоков включает наши служебные и не обнулится никогда.
`h3session_accepts_request` уже отказывает всему, что старше id из GOAWAY, так
что дренаж ограничен тем, что успело начаться. Соединение без h3 над ним
закрывается сразу — заканчивать нечего.

Новые соединения во время дренажа получают `CONNECTION_REFUSED` (та же функция,
что и на переполнении), а не тишину.

Проверено вживую: `SIGTERM` при живом h3-соединении → в логе `GOAWAY sent, no
requests past stream 4`, затем `CONNECTION_CLOSE 0x0`, процесс выходит примерно
через секунду вместо того, чтобы досиживать пятисекундное окно.

**Сделано (2026-08-09): перенос ключей через перезагрузку.** `quic_policy_init()`
разделилась надвое. **Настройки** перечитываются на каждый вызов — в этом смысл
перезагрузки. **Таблица соединений и оба ключа** создаются один раз на процесс и
переживают перезагрузку.

Ключи — то, ради чего пункт и был записан: токен stateless reset это
`HMAC(reset_key, cid)`, а `NEW_TOKEN` запечатан под `token_key`, и оба лежат у
пиров. Смена ключей превращает всё выданное в шум: пир, получивший reset, больше
его не узнаёт и ретранслирует в пустоту до idle-таймаута, а клиент с `NEW_TOKEN`
платит тот самый round trip, ради отмены которого токен и выдавался.

Таблица оказалась не деградацией, а багом. Эндпоинты берут указатель на неё в
долг при создании, а мягкая перезагрузка оставляет прежних воркеров дренажить
свои соединения через эти эндпоинты — то есть `quic_policy_free()` вырывал
таблицу маршрутизации из-под живых соединений, а пересоздание вдобавок теряло
все записи в ней. Функция удалена: вызывать её было бы опасно, а звать её теперь
некому.

Размер уже созданной CID-таблицы не меняется при soft reload, но admission
limit перечитывается и действует глобально на все endpoint/worker поколения.
Изменение размера самой таблицы потребовало бы безопасного параллельного
rehash, поэтому для полной смены её capacity всё ещё нужен рестарт процесса.

**Оговорка про `reload: soft` и SO_REUSEPORT, найденная живой проверкой.**
Дренаж и перезагрузка требуют здесь противоположного. При остановке порт никто не
занимает, поэтому сокет остаётся открытым и дообслуживает свои соединения. При
перезагрузке эндпоинты новой конфигурации **уже привязаны к тому же порту** под
`SO_REUSEPORT`, а ядро раскладывает клиентов по сокетам группы хешем 4-tuple:
дренажный сокет, оставшийся в группе, отказывает всему, что на него попало, и
ретрансмиссии клиента попадают туда же — то есть он не доходит до экземпляра,
который мог бы его обслужить (проверено: второе соединение получало
`CONNECTION_CLOSE 0x2`). Поэтому при перезагрузке старый эндпоинт **выходит из
группы**, как и раньше, — ценой соединений, которые он ещё держал.

Проверено вживую: строка `connection table and keys created` печатается **ровно
один раз на процесс** (её и добавили, чтобы это было наблюдаемо), а
`quicclient --new-token --pause 6000` с `SIGUSR1` посередине показывает
`second connection retried: no` — токен, выданный до перезагрузки, принят после
неё. Ветка `SIGTERM` не задета: `GOAWAY` и выход за ~1 с.

**Осталось по §5:** сохранение h3-соединений через `reload: soft` — сегодня они
рвутся, и починка требует передачи владения сокетом между конфигурациями, а не
ещё одного флага. И проверка дренажа под нагрузкой — вместе с фазой 8.

## 6. Совместное существование h1.1 / h2 / h3

- TCP-порт продолжает обслуживать h1.1 и h2 (ALPN), UDP-порт — только h3.
- ALPN-колбэк: для QUIC-`SSL` предлагается **только** `h3`; для TCP —
  прежний порядок `h2` → `http/1.1`. Смешение недопустимо (`03` §2.2).
- Клиент, у которого h3 не проходит (UDP заблокирован), молча остаётся на TCP —
  это и есть штатное поведение Alt-Svc. Никакой логики fallback на сервере не
  требуется.
- `H3_VERSION_FALLBACK` (0x0110) отправляем, если запрос по h3 обязан быть
  обслужен более старой версией, — на практике не используется.

## 8. Критерии готовности фазы

1. Браузер, зайдя по TCP, видит `Alt-Svc` и на следующем запросе переходит на h3
   (проверяется в DevTools: Protocol = `h3`).
2. `/metrics` показывает секции `quic` и `http3` с ненулевыми значениями.
3. Мягкая перезагрузка не рвёт активные h3-соединения посреди запроса.
4. Отключение `http3.enabled` в конфиге и reload убирает UDP-сокет.
5. Нагрузочный прогон (`h2load --npn-list=h3` / `quiche-client`) 10 000 запросов
   без утечек под ASan и без гонок под TSan.
