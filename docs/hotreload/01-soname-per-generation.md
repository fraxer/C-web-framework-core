# Модуль приложения на горячую: свой SONAME каждому поколению

Реализовано 2026-09-07; замеры сделаны тогда же и воспроизводимы. Продолжение
[00-shadow-copy.md](00-shadow-copy.md), который закрыл обработчики и уперся на
модуле — разбор в его §8.2. Что вышло иначе, чем задумано, — в §7.

## 1. Задача

Теневые копии подхватывают пересобранный обработчик, но не модуль приложения из
`main.modules`. Наивная копия модуля даёт не новое поколение кода, а **смесь
двух**. Стенд повторяет форму cwfr: `libapp.so` с `SONAME libapp.so`, обработчик
слинкован `-lapp`; во втором поколении **обе** библиотеки загружены теневыми
копиями:

```
поколение 1:  app_init -> middleware=v1   обработчик -> model=v1
поколение 2:  app_init -> middleware=v2   обработчик -> model=v1   <—
```

Копия сработала: `app_init()` второго поколения — из новой сборки, и
зарегистрированные им middleware и деструкторы контекстов ведут в новый код. Но
обработчик того же поколения зовёт `model_get()` из **старой**. Один запрос
ходит в две сборки сразу.

Второе следствие тяжелее первого: новые обработчики держат зависимость на старый
модуль, поэтому он больше никогда не выгружается. Отображения растут на каждую
пересборку — прямое нарушение критерия «многократная перезагрузка не наращивает
отображения»:

```
после поколения 1        app=1 handler=1
после поколения 2        app=2 handler=2
после гашения 1          app=2 handler=1   ← модуль остался
```

### Почему теневой копии здесь мало

Код из `.so` достаётся двумя независимыми путями, и 00-й план разбирает только
первый.

1. **`dlopen(путь)` + `dlsym(handle, имя)`.** Дедупликация по строке пути и по
   `(st_dev, st_ino)`. Теневая копия её обходит — новое имя и новый inode.
   Обработчик достаётся только так, поэтому для обработчиков этого хватает.
2. **`DT_NEEDED` по `SONAME`.** Обработчик слинкован с модулем
   (`cwfr_add_handlers(LINK_LIBS cwfr::framework app)`), и компоновщик записал в
   него не путь, а `SONAME` модуля. При загрузке обработчика `_dl_map_object`
   ищет среди **уже загруженных** объектов первый, у кого совпадает `l_name` или
   `DT_SONAME`, и совпадение находится **до открытия файла** — проверка по inode
   туда не доходит. Список загруженных пополняется с конца, значит старый модуль
   в нём всегда раньше копии.

`SONAME` живёт внутри ELF и переезжает в копию вместе с байтами. Поэтому копия
меняет всё, что смотрит первый путь, и ничего — из того, что смотрит второй.

### Чего пробовать не стоит

* **`RTLD_GLOBAL` вместо `DT_NEEDED`** (обработчики без `-lapp`, символы из
  глобальной области). Глобальная область просматривается в том же порядке
  загрузки — старый модуль снова первый.
* **`dlmopen` в отдельное пространство имён на поколение.** Изолирует всё, включая
  `libcwfr_framework.so`: пулы БД, `appconfig`, i18n удвоятся. Разделить объект
  между пространствами имён glibc не умеет.
* **Погасить старое поколение перед постройкой нового** (чтобы модуль успел
  выгрузиться). Под `reload: hard` это работает, под `soft` — нет:
  `multiplexingserver.c:85` снимает слушающие сокеты сразу по флагу `shutdown`, а
  дальше воркер крутится, пока `connection_count` не дойдёт до нуля, то есть пока
  живы keep-alive, WebSocket и h3-сессии. Ожидание этого нуля — окно произвольной
  длины, в котором не слушает никто; сейчас это окно измеряется миллисекундами.
  Причём проблема рекурсивна: модуль выгружаем только когда его не держит **ни
  одно** поколение, а новое всегда создаётся раньше смерти старого. Момента с
  нулём поколений при живом трафике не бывает — его можно только изготовить, и
  это и есть то самое окно.

Остаётся единственное: раз связывание идёт по `SONAME`, дать каждому поколению
свой.

## 2. Что предлагается

Копия модуля получает пропатченный `DT_SONAME`, копии зависящих от него
обработчиков — тот же тег в своих `DT_NEEDED`. Строка переписывается **на месте,
той же длины**, поэтому смещения, размеры секций и всё остальное в файле не
двигаются.

Тег — последние два байта строки: `libapp.so` → `libapp.01`. Проверено на стенде
из §1, те же две библиотеки, копии пропатчены:

```
патчим копии поколения 2 (тег 01, длина строки сохранена):
  SONAME: libapp.so -> libapp.01      (.shadow-libapp.so)
  NEEDED: libapp.so -> libapp.01      (.shadow-lib_handler.so)

поколение 1:  app_init -> middleware=v1  обработчик -> model=v1
поколение 2:  app_init -> middleware=v2  обработчик -> model=v2   <—

после гашения поколения 1:
  отображений app: 1
  поколение 2 отвечает: middleware=v2 / model=v2
после гашения поколения 2:
  отображений app: 0
```

Смесь исчезла, старый модуль выгрузился вместе со своим поколением, ничего не
осталось.

### 2.1 Занятость тега проверяется загрузчиком, а не нами

Тег должен быть уникален среди **живых** поколений. Отдельный учёт не нужен и
был бы неприятен: поколение освобождается на рабочем потоке, из
`appconfg_threads_decrement()`, и возвращать оттуда тег пришлось бы под
синхронизацией. Вместо этого спрашиваем загрузчик:

```c
void* h = dlopen("libapp.01", RTLD_LAZY | RTLD_NOLOAD);   /* имя без слэша -> поиск по SONAME */
if (h != NULL) { dlclose(h); /* тег занят */ }
```

Проверено на том же стенде:

```
тег libapp.01 до всего:              свободен
тег libapp.01 при живом поколении 2: занят
после гашения поколения 2:           свободен
```

Освобождение получается ровно тогда, когда модуль действительно выгружен, без
единой строки учёта и без блокировок.

### 2.2 Что именно копируется

Тег меняет `DT_NEEDED`, поэтому при пересборке модуля копировать приходится **и
зависящие от него обработчики, даже неизменившиеся**. Копировать всё подряд не
нужно: `--as-needed` оставляет запись только у тех, кто действительно зовёт код
модуля. В этом репозитории это 5 файлов из 15:

```
обработчиков: 15
с NEEDED libapp.so: auth, middleware, models/modeluser, models/modeluserview, ws/wsindex
без него: session, bench x3, db, email, files, httpclient, index, json
```

Цена поколения при пересборке `libapp.so`:

```
  libapp.so (модуль)               44752
  auth/lib_auth.so                 17080
  middleware/lib_middleware.so     15704
  models/lib_modeluser.so          16576
  models/lib_modeluserview.so      16944
  ws/lib_wsindex.so                16400
  ------------------------------------
  итого                           127456 байт (124 КБ)
```

Правило общее и рекурсивное: копируется и перетегируется всё, чей `DT_NEEDED`
называет перетегированный `SONAME` — включая случай, когда один модуль зависит от
другого.

## 3. Дизайн

### 3.1 Карта переименований принадлежит поколению

`shadowload` получает необязательный аргумент — карту `SONAME -> SONAME`,
которую строит и владеет строящаяся конфигурация:

```c
typedef struct shadow_sonames shadow_sonames_t;   /* список пар, непрозрачный */

shadow_sonames_t* shadow_sonames_create(void);
/* Подобрать свободный тег для `soname` и записать пару. */
int  shadow_sonames_add(shadow_sonames_t* map, const char* soname);
void shadow_sonames_free(shadow_sonames_t* map);

void* shadow_dlopen_ex(const char* path, int flags, const char* tmpdir,
                       const shadow_sonames_t* map);
```

`shadow_dlopen()` остаётся как `shadow_dlopen_ex(..., NULL)` — поведение 00-го
плана без изменений.

`shadow_dlopen_ex` с непустой картой:

1. смотрит `DT_SONAME` файла и его `DT_NEEDED`; если ни одно имя в карте не
   встречается — ведёт себя как обычный `shadow_dlopen` (копия только при
   пересборке);
2. если встречается — копия делается **всегда**, даже когда файл не менялся:
   его `DT_NEEDED` обязан указывать на тег этого поколения;
3. патчит копию (§3.2) и грузит её.

### 3.2 Патч

Разбор минимальный: `PT_DYNAMIC` из таблицы программных заголовков, `DT_STRTAB`
переводится в файловое смещение по `PT_LOAD`, дальше обход `.dynamic`. Пишутся
строки по смещениям из `DT_SONAME`, `DT_NEEDED` и `vn_file` в `.gnu.version_r` —
последнее на случай версионированных символов модуля (у `libapp.so` их сейчас
нет: в `.gnu.version_r` обработчика значится только `libc.so.6`).

Поддерживаются ELF32 и ELF64 обоих порядков байт — сборка под ARM в проекте
живая (см. память про Banana Pi), и хотя патч выполняется на той же машине, где
работает сервер, разрядность читается из заголовка, а не предполагается.

### 3.3 Склейка строк в `.dynstr` — единственный настоящий риск

GNU ld (проверено на 2.46) выполняет **суффиксную склейку**: если библиотека
зависит и от `mylibapp.so`, и от `libapp.so`, в `.dynstr` лежит только первая
строка, а второй `DT_NEEDED` указывает внутрь неё:

```
NEEDED: libapp.so
NEEDED: mylibapp.so
.dynstr: только [0x6e] mylibapp.so
смещение "mylibapp.so": 1086
смещение "libapp.so"  : 1088     <— на два байта внутрь
склеены хвостом: ДА
```

Патч на месте в таком файле испортил бы и `mylibapp.so`. Значит перед записью
обязательна проверка: байт перед началом строки должен быть `\0`, и ни одно
другое имя из `.dynamic` не должно попадать в переписываемый диапазон.

Дописать строку в конец `.dynstr` нельзя — размер секции менять нельзя, а
свободного хвоста там практически нет: у реального обработчика `.dynstr` 1704
байта и **3** нулевых байта в конце. Поэтому при обнаружении склейки —
**отказ**: поколение строится по-старому, без перетегирования, в лог уходит
внятное сообщение с именами обеих библиотек. Модуль в этой перезагрузке не
меняется, всё остальное меняется. В реальных обработчиках cwfr склейки нет —
`libapp.so` лежит отдельной строкой (`[0x226]`, следующая `[0x230]`), один раз в
файле, перед ней `\0`.

Другие компоновщики (lld, mold) склейку тоже умеют, поэтому проверка нужна
всегда, а не только для GNU ld.

### 3.4 Выбор тега

Последние два байта строки `SONAME`, base36 — 1296 значений, освобождаются сами
(§2.1). Требования и отказы:

* строка `SONAME` короче трёх байт — тег вписать некуда, отказ;
* два модуля одного поколения, чьи `SONAME` различаются только в последних двух
  байтах, после перетегирования совпали бы — проверяется до патча, отказ;
* все 1296 тегов заняты — практически недостижимо (это 1296 живых поколений),
  отказ.

Отказ везде означает одно и то же: перезагрузка происходит, модуль остаётся
прежним, причина в логе.

### 3.5 Остаток §3.4 плана 00 наконец применим

Теперь у каждого поколения свой экземпляр модуля, и всё, что 00-й план
предполагал, становится и осмысленным, и обязательным:

* **список модулей** переезжает из статической `__modules` в `appmodule.c` в
  `appconfig_t`, освобождается в `appconfig_clear()` рядом с
  `routeloader_free(taskmanager_loader)` — то есть когда ушёл последний поток
  поколения и middleware старого модуля никто исполнять уже не может;
* **коллбеки контекстов** (`httpctx_set_user_data_free()`,
  `wsctx_set_user_data_free()`) переезжают из статических переменных
  `protocols/http/httpcontext.c` и `protocols/websocket/wscontext.c` в поля
  `appconfig_t`. Сейчас они глобальны и отклоняют регистрацию другого адреса, а у
  пересобранного модуля адрес деструктора другой — то есть без этого переезда
  перезагрузка модуля отклонялась бы сама собой;
* доставка коллбека в точку вызова — обратной ссылкой `server_t -> appconfig_t`,
  проставляемой при разборе `servers`; `httpctx_init()` / `wsctx_init()` получают
  его параметром и хранят в самом контексте, чтобы доживающий запрос не зависел
  от глобального состояния. Три точки создания контекста в ядре
  (`httpserverhandlers.c`, `websocketsserverhandlers.c`, `httpclient.c` — у
  клиента `NULL`) плюс тесты.

Хранение остаётся в конфигурации, а глобальной переменной живёт только адрес
«того, что сейчас собираем»: `app_init()` вызывается до `appconfig_set()`,
загрузка однопоточна и идёт под `module_loader_signal_lock()`.

### 3.6 Проверочный проход и повторное использование копий

`module_loader_config_correct()` грузит всё отдельным поколением и тут же его
выбрасывает (00 §8.3). Значит проверочный проход тоже подберёт тег, сделает
копии и освободит тег при `dlclose`. Настоящий проход подберёт, скорее всего, тот
же тег.

Ключ повторного использования копии, введённый в 00 §8.3, — состояние файла;
теперь к нему добавляется **тег**. Тогда настоящий проход находит копии,
сделанные проверочным, и просто грузит их снова, как это уже работает для
обработчиков.

## 4. Шаги реализации

1. **Патчер ELF** — `core/src/moduleloader/elfsoname.{c,h}`: чтение
   `DT_SONAME`/`DT_NEEDED`/`.gnu.version_r` и переименование на месте с проверкой
   склейки (§3.3). Отдельный файл и отдельные тесты: это единственная часть,
   работающая с байтами формата.
2. **Карта переименований** — `shadow_sonames_*` и `shadow_dlopen_ex()` в
   `shadowload.{c,h}`; `shadow_dlopen()` сводится к вызову с `NULL`. Ключ
   повторного использования копии расширяется тегом (§3.6).
3. **Модуль приложения** — `appmodule.c`: `shadow_dlopen_ex`, список модулей в
   `appconfig_t`, освобождение в `appconfig_clear()`. `main.tmp` читается прямо из
   json-документа: `app_modules_load` вызывается до `appconfig_set`.
4. **Коллбеки контекстов** — в `appconfig_t`, обратная ссылка
   `server_t -> appconfig_t`, новая сигнатура `httpctx_init()` / `wsctx_init()`
   (§3.5).
5. **Обработчики** — карта поколения передаётся в `routeloader_load_lib()` рядом
   с `tmpdir`, дальше через те же пять статических функций `moduleloader.c`.
6. **Тесты** — `core/tests/unit/`: переименование на месте, отказ при склейке
   (собрать пару библиотек с суффиксными `SONAME`, как в §3.3), подбор и
   освобождение тега через `RTLD_NOLOAD`, отказ при коротком `SONAME`. Сквозной
   сценарий — в `tests/hot_reload_shadow.sh`: пересборка модуля с изменением
   ответа обработчика и с изменением деструктора контекста.
7. **Документация** — `hot-reload.md` и `config.md` обеих локалей: раздел «Модуль
   приложения» переписать (сейчас он объясняет, почему так нельзя), добавить
   оговорку про отказ при склейке и про то, что `ldd` покажет тег. `INSTALL.md`
   §7 — про смену сигнатуры `httpctx_init()`/`wsctx_init()`.

## 5. Критерии готовности

* пересобранный на месте модуль из `main.modules` подхватывается по `SIGUSR1`, и
  обработчик нового поколения зовёт **новый** код модуля;
* под `reload: soft` перезагрузка с пересборкой модуля не создаёт окна, в котором
  никто не слушает;
* старое поколение выгружается целиком: `/proc/PID/maps` после серии пересборок
  показывает один экземпляр модуля, RSS ровный;
* перезагрузка с пересобранным модулем, регистрирующим деструктор контекста,
  проходит;
* обработчик, не зависящий от модуля, не копируется при пересборке модуля;
* библиотека со склеенными строками в `.dynstr` не патчится, перезагрузка
  проходит без смены модуля, причина в логе;
* отчёт ASan для обработчика и для модуля содержит имя функции, файл и строку;
* `ctest` — все наборы; Debug с ASan и `-fanalyzer` — без предупреждений;
* `tests/ci.sh hotreload` — зелёный.

## 6. Риски и границы

* **Патченый ELF не пройдёт проверку подписи.** IMA appraisal, dm-verity,
  SELinux-политики на исполняемые отображения увидят файл, которого не подписывал
  никто. Теневые копии сами по себе уже создают такой файл (00 §2), но там байты
  совпадают с оригиналом, и хеш-политика ещё могла бы сойтись; здесь нет. Там,
  где такие политики включены, перезагрузка модуля должна отключаться —
  предположительно ключом в `main.env`.
* **`ldd` и отладчик покажут `libapp.01`.** Косметика: `l_name` остаётся путём
  копии, `.note.gnu.build-id` не трогается и совпадает с оригиналом, поэтому
  символизация и поиск отдельных debug-файлов работают. Проверить это отдельным
  замером, как в 00 §2.
* **Статический TLS.** Каждое поколение — новый объект в процессе. Если
  приложение использует `__thread` с моделью initial-exec, серия перезагрузок
  может упереться в `cannot allocate memory in static TLS block`: запас
  выделяется при старте процесса и не растёт. Стоит замерить, сколько поколений
  переживает модуль с одной такой переменной, и назвать число в документации.
* **Копии на диске.** 124 КБ на поколение в этом репозитории (§2.2), удаляются
  при завершении процесса, как и в 00 §3.3. Верхняя граница — число пересборок
  модуля за время жизни процесса.
* **Компоновщик может склеить строки** — §3.3. Отказ безопасен, но означает, что
  на некоторых приложениях перезагрузка модуля не заработает, и узнают об этом
  только по логу. Стоит дать способ проверить заранее: маленькая проверка в
  `migrate` или отдельная подкоманда, которая скажет, патчатся ли `.so` этого
  приложения.
* **Порядок инициализации приложения.** Каждое поколение выполняет `app_init()`
  своего экземпляра модуля, то есть конструкторы ELF и статические инициализаторы
  выполняются заново. Приложение, которое держит состояние в статических
  переменных модуля и рассчитывает на его сохранность между перезагрузками, этого
  не получит — состояние у каждого поколения своё. Это правильное поведение, но
  его нужно назвать в документации явно.

## 7. Что вышло иначе

### 7.1 Резервировать тег надо по пути, а не по «файл изменился»

`shadow_needs_copy()` из 00-го плана отвечает «файл отличается от запомненного».
Для резервирования тега этого не хватает, и ошибка проявляется ровно один раз —
зато полностью: перезагрузка делала копии и модуля, и обработчика, а сервер
продолжал отвечать старым кодом.

Причина в том, что `module_loader_config_correct()` — полноценный проход: он
резервирует тег, грузит патченые копии, и всё это выбрасывает. Заодно он
**обновляет запись** о файле. Настоящий проход после него видит «файл не менялся»,
тега не берёт, а копию всё равно делает — непатченую. Обработчики связываются со
старым модулем, и получается ровно та смесь, ради ухода от которой всё затевалось.

Правильный вопрос — не «изменился ли файл», а «отличается ли объект,
зарегистрированный по этому пути, от файла, который там лежит». Второе условие
устойчиво: объект после загрузки не меняется, поэтому «прошлое решение было
копией» (`entry->copy != NULL`) означает расхождение навсегда. Отсюда
`__shadow_path_stale()` и `shadow_sonames_reserve()`, который принимает **путь**,
а не `SONAME`, и решает:

* объект по пути и есть этот файл — тега не нужно, имя ни с чем не спутать;
* копия уже есть и всё ещё годна — берётся **её** имя, и новое поколение
  разделяет ту же библиотеку вместо второго экземпляра. Это же даёт бесплатную
  перезагрузку без пересборки и переиспользование копий проверочного прохода;
* файл действительно пересобран под живым поколением — новый свободный тег.

### 7.2 Проверочный проход обязан грузить модули

§3.6 предполагал, что достаточно учесть тег в ключе повторного использования. На
деле проверочный проход загружает обработчики, а их `DT_NEEDED` после патча
называет тег, которого в процессе нет, — `dlopen` не найдёт такой библиотеки и
проверка провалится на здоровой конфигурации.

Поэтому `app_modules_check()` теперь не «открыть и закрыть каждый модуль», а
«открыть модули в проверочную конфигурацию и убедиться, что каждый экспортирует
`app_init()`» — не вызывая его. Проверочное поколение живёт до `appconfig_free()`
и закрывает их само. Побочно это лучше прежнего: проверка выполняется над той же
конструкцией, что и настоящая загрузка, а не над её половиной. Порядок в
`module_loader_config_correct()` пришлось поменять — модули проверяются **до**
`module_loader_config_load()`, иначе обработчикам не к чему привязываться.

### 7.3 Отказ переименования не отменяет перезагрузку

§3.3 обещал: при склейке строк поколение строится по-старому, а не отклоняется.
Сделано двухпроходной валидацией: `module_loader_config_correct()` при отказе
именно по этой причине (`shadow_retag_refused()`) выключает переименование на весь
процесс (`shadow_retag_disable()`) и повторяет проход целиком. Дальше
`shadow_sonames_add()` отказывает всем, `__app_module_open()` видит пересобранный
модуль без тега и **оставляет работать прежний** — вместо копии, которая дала бы
смесь. Всё остальное в перезагрузке применяется.

Тот же путь обслуживает модуль без `SONAME`.

### 7.4 Проверка склейки оказалась проще и полнее

§3.3 предполагал две проверки: байт перед строкой и отсутствие чужих ссылок
внутрь диапазона. Вторая не нужна и доказуемо: строка в `.dynstr` начинается либо
с нуля, либо сразу после `\0`, а внутри нашей строки `\0` нет — значит внутри
неё никакая другая начаться не может. Остаётся одна проверка, `data[at-1] == 0`,
и она полна. Плюс равенство длин, без которого писать нельзя.

### 7.5 Проверочный проход обязан ещё и вызывать `app_init()`

Обнаружилось уже на живом сервере, по сообщению
`__module_loader_middlewares_load: failed to find middleware <имя>`. Пока модуль
не перезагружался, ограничение «нельзя одной перезагрузкой добавить и middleware,
и маршрут с ним» было честным: имён новой сборки взять неоткуда. Как только
модуль стал подхватываться, оно превратилось в дефект — код с новым middleware
уже в процессе, а проверочный проход всё ещё сверяется с реестром работающего
поколения и отклоняет перезагрузку.

Воспроизведение: модуль версии 1 регистрирует `mw_a`, версии 2 — `mw_a` и `mw_b`;
пересборка модуля вместе с добавлением `"mw_b"` в конфиг даёт
`failed to find middleware mw_b`, сервер продолжает работать на старой
конфигурации.

Починено тем, что `app_modules_check()` теперь вызывает `app_init()`, а
`__module_loader_config_attempt()` на время прогона откладывает реестр в сторону
(`middleware_registry_save()` / `middleware_registry_restore()` — снимок массива
на 256 записей). Порядок важен: реестр возвращается **до** `appconfig_free()`,
иначе он какое-то время указывал бы внутрь уже выгруженных модулей.

Цена — `app_init()` за перезагрузку выполняется дважды. Дублей регистрации не
возникает: оба прогона начинаются с пустого реестра. Побочные действия, если они
есть, удваиваются — это названо в документации.

### 7.6 Что подтвердилось замерами

Сквозной `tests/hot_reload_shadow.sh` на живом сервере:

```
== the application module is picked up when it is rebuilt in place
  ok    the handler of the new generation calls the rebuilt module
  ok    the handler that does not need the module is unaffected
  ok    a middleware introduced by that same build is in force
  ok    and was not copied for the module's sake
  ok    2 module object(s) after three swaps -- old generations unloaded

== a soft reload that swaps the module never stops answering
  ok    every request during the swap was answered
  ok    and the new module is what answers once the reload has landed
```

Юнит-наборы в `tests/unit/test_shadowload.c`: переименование на месте (включая
проверку через сам загрузчик — объект отвечает на новое имя и не отвечает на
старое), отказ при другой длине, отказ на склеенных строках (фикстура
`libxxlibshadowdep.so` + `libshadowdep.so`, склейка подтверждена в собранном
файле), занятость и освобождение тега через `RTLD_NOLOAD`.

Оба набора зелёные в Release и в Debug с ASan/`-fanalyzer`, без предупреждений и
без находок санитайзера.
