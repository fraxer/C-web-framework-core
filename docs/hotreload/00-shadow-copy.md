# Перезагрузка кода модулей и обработчиков через теневые копии

Реализовано 2026-09-07, **кроме §3.4** — теневых копий для модуля приложения:
приём там не работает в принципе, разбор и замер в §8. Замеры в §1–2 сделаны
2026-09-07 и воспроизводимы.

## 1. Задача

`SIGUSR1` перечитывает конфигурацию, но **не подхватывает пересобранный `.so`** —
ни обработчик, ни модуль приложения из `main.modules`. В процессе остаётся прежний
код, и повторные сигналы этого не меняют:

```
старт (на диске v1):            X-Mod-Ver: 1   handler 1
пересобрал оба в v2, SIGUSR1:   X-Mod-Ver: 1   handler 1
пересобрал в v3, SIGUSR1 ×3:    X-Mod-Ver: 2   handler 2
```

Свежий старт при этом честно берёт то, что лежит на диске.

### Почему так

`dlopen()` считает библиотеку уже загруженной по двум признакам, в таком порядке:

1. **по строке пути** — сравнение с именами загруженных объектов **до** открытия
   файла. Проверено: `gcc -o` при пересборке создал новый inode (109613 → 109619),
   а `dlopen` того же пути вернул прежний объект со старым кодом;
2. **по паре `(st_dev, st_ino)`** — уже после открытия. Отсюда:

```
оригинал        handle=0x...475030  v1
симлинк         handle=0x...475030  v1     ← тот же объект
жёсткая ссылка  handle=0x...475030  v1     ← тот же объект
копия           handle=0x...477470  v1     ← новый объект
другой файл     handle=0x...478540  v2     ← новый объект
```

Значит подменить код можно только новым именем **и** новым inode одновременно.
Симлинки, жёсткие ссылки и перезапись поверх того же пути бесполезны.

Вторая причина, специфичная для нас: даже когда объект выгружается
(`routeloader_free` вызывает `dlclose`), счётчик ссылок не падает до нуля —
новое поколение конфигурации загружает обработчики **раньше**, чем освобождается
старое. Модуль приложения не выгружается вообще и намеренно: старые рабочие
потоки могут исполнять его middleware, а зарегистрированные указатели ведут
внутрь его кода.

## 2. Почему теневые копии, а не memfd

Оба приёма дают новое имя и новый inode. Разница — в отладке. Один и тот же
use-after-free в загруженной библиотеке, отчёт ASan:

```
обычный dlopen:   #0 0x... in trigger_uaf .../uaf.c:8
memfd:            #0 0x...  (/proc/self/fd/4+0x127c)
теневая копия:    #0 0x... in trigger_uaf .../uaf.c:8
```

memfd теряет имена, файлы и строки именно для прикладного кода — того, ради
которого Debug-сборка и включает ASan. GDB в batch-режиме на такой библиотеке
**зависает**: не найдя файла, упирается в промпт debuginfod на отсутствующем
stdin.

Восстановить символы через `addr2line` по файлу на диске можно, но это ловушка:
memfd нужен ровно тогда, когда файл на диске **пересобран** и больше не
соответствует загруженному коду. `addr2line` выдаст правдоподобный и неверный
ответ, ничего не сообщив о расхождении.

| | memfd | теневая копия |
|---|---|---|
| Подхватывает пересобранный `.so` | да | да |
| ASan, gdb, perf, core dump | нет | **да** |
| `$ORIGIN` в RPATH | сломан | **сохраняется**, если копия рядом с оригиналом |
| Реакция EDR / SELinux `execmem` | подозрительно | обычная загрузка |
| Следы на диске | нет | временный файл на время жизни библиотеки |

Проверено отдельно: копия рядом с оригиналом сохраняет `$ORIGIN` — зависимость,
лежащая в том же каталоге, находится. Копия в `/tmp` — нет.

Системных библиотек это не касается вовсе: `libargon2.so.1` и подобные ищутся
через `ldconfig`, а не через `$ORIGIN`, и грузятся одинаково в обоих вариантах.

## 3. Дизайн

### 3.1 Копировать только когда нужно

При обычном старте путь ещё не загружен — грузим напрямую, поведение не меняется
вообще. Копия делается, только если выполнены **оба** условия:

* путь уже загружен в этом процессе — проверяется `dlopen(path, RTLD_NOLOAD)`;
* файл на диске изменился — сравнение `(st_dev, st_ino, st_mtime, st_size)`
  с запомненными при прошлой загрузке.

Так копии появляются строго при реальной пересборке, а не на каждой перезагрузке.

### 3.2 Куда класть

Рядом с оригиналом: `<каталог оригинала>/.cwfr-shadow-<pid>-<seq>.so`. Это
сохраняет `$ORIGIN`.

Если каталог недоступен на запись (типично для `/opt`) — откат в `main.tmp` с
сообщением в лог о том, что `$ORIGIN` в этой загрузке не действует.

`main.tmp` при загрузке модулей ещё не опубликован через `env()`: `app_modules_load`
вызывается до `appconfig_set`. Значение читается напрямую из json-документа,
который на этом шаге уже разобран.

### 3.3 Время жизни

Файл **нельзя** удалять сразу после `dlopen` — без файла на диске отладчик
оказывается ровно в положении memfd, ради ухода от которого всё и затевалось.

Удаление происходит в двух точках, и обе — вне жизненного цикла поколения:

* **при завершении процесса** — штатный выход удаляет все копии, которые сделал;
* **при старте** — обход каталогов, где лежат загружаемые `.so`, и удаление
  файлов по префиксу `.cwfr-shadow-`, чей pid отсутствует в системе. Это
  подчищает остатки после `kill -9` и падений.

То есть копия переживает выгрузку самой библиотеки. Сделано намеренно: пока
процесс жив, на диске лежат файлы **всех** поколений, и core dump
символизируется целиком, включая кадры кода, который уже выгружен.

**Память при этом не течёт.** Отображение снимается по `dlclose` вместе с
поколением — проверено: 5 загрузок → 5 отображений, 5 `dlclose` → 0 отображений.
Переживает выгрузку только файл на диске, а его размер — размер `.so`.

Расход диска ограничен числом пересборок за время жизни процесса: копия
появляется лишь тогда, когда файл действительно изменился (§3.1), а не на каждой
перезагрузке.

### 3.4 Модули привязываются к поколению конфигурации

Теневая копия для модуля бессмысленна, пока модуль глобальный: старый экземпляр
не выгружается, новый добавляется к нему, и каждая перезагрузка стоит копии в
памяти и файла на диске. Поэтому список модулей переезжает из глобальной
статической переменной `appmodule.c` в `appconfig_t` — ровно тем же приёмом,
каким там уже живёт `routeloader_lib_t* taskmanager_loader`.

Освобождение — в `appconfig_clear()`, куда управление приходит из
`appconfg_threads_decrement()`, когда ушёл последний поток поколения. К этому
моменту никто уже не может исполнять middleware старого модуля, и `dlclose`
безопасен.

Если файл не менялся, `shadow_dlopen` вернёт тот же объект и лишь увеличит
счётчик ссылок — новое поколение разделит библиотеку со старым, а `dlclose`
старого просто уменьшит счётчик. Копия появляется только при реальной
пересборке, и тогда у каждого поколения свой экземпляр, освобождаемый вместе с
ним.

#### Коллбеки контекстов переезжают в конфигурацию

`httpctx_set_user_data_free()` хранит **глобальный** указатель и отклоняет
попытку зарегистрировать другую функцию. При пересборке модуля адрес деструктора
в новой копии другой, поэтому перезагрузка отклоняется. Проверено:

```
старт:              X-D: d1
после смены модуля: (пусто)
лог: httpctx_set_user_data_free: a different destructor is already registered
     app_init(d2): деструктор занят
     app_modules_load: app_init() failed in .../libd2.so
```

Раз модуль теперь принадлежит поколению, туда же принадлежит и то, что он
зарегистрировал. Коллбеки переезжают из статических переменных
`protocols/http/httpcontext.c` и `protocols/websocket/wscontext.c` в поля
`appconfig_t`.

Это лучше сброса глобальной переменной по двум причинам. Сброс оставлял окно, в
котором доживающий поток старого поколения освобождал бы свой payload
деструктором нового; при хранении в конфигурации каждый поток работает со своим
поколением, и окна нет. И конфликт двух модулей **внутри одного** поколения
по-прежнему диагностируется — поле уже занято в этом конфиге.

**Как коллбек попадает в точку вызова.** Во всех трёх местах, где создаётся
контекст, доступен `server_t*`:

| Файл | Что рядом |
|---|---|
| `protocols/http/server/httpserverhandlers.c:~1039` | `data->server` |
| `protocols/websocket/server/websocketsserverhandlers.c:~588` | `data->server` |
| `protocols/http/client/httpclient.c:~806` | `server` |

Значит достаточно обратной ссылки `server_t -> appconfig_t`, проставляемой при
разборе `servers`. `httpctx_init()` получает коллбек параметром и кладёт его в
сам контекст, а `httpctx_clear()` берёт оттуда — контекст становится
самодостаточным и не зависит от того, что происходит с глобальным состоянием,
пока запрос доживает. Клиент передаёт `NULL`: `ctx->user_data` он не использует.

**Куда пишет `httpctx_set_user_data_free()`.** Она вызывается из `app_init()`,
когда конфигурация ещё строится и не опубликована через `appconfig_set()`.
Ядро держит указатель на строящуюся конфигурацию на время загрузки — она
однопоточна и идёт под `module_loader_signal_lock()`, так что отдельной
синхронизации не нужно. Хранение при этом остаётся в конфигурации; глобальной
переменной живёт только адрес «того, что сейчас собираем».

## 4. Отдельно и раньше: отказ при загрузке модулей убивает сервер

Дефект существует в текущем коде и к теневым копиям отношения не имеет. Чинить
его следует до всего остального.

`app_modules_load()` вызывается из `module_loader_init()`, то есть **за
пределами** `module_loader_config_correct()` — той самой проверки, ради которой
плохая конфигурация отклоняется до того, как старое поколение будет погашено.
Порядок в `signal_reload()` таков, что при `reload: hard` сокеты закрываются
раньше, чем строится новая конфигурация. Если загрузка модулей провалится,
старого поколения уже нет, а нового не будет.

Достаточно опечатки в пути:

```
до:  HTTP 200
после reload с битым путём модуля:
     HTTP 000   процесс: жив   порт: не слушается
     лог: app_modules_load: can't load module /нет/такого.so: ...
```

Процесс остаётся живым и не обслуживает ничего. Супервизор такого не заметит.

До появления `main.modules` этот путь тоже мог отказать (`middlewares_init()`
возвращал `0`), но у вкомпилированного приложения это была ошибка программы, а
не конфигурации. Путь из `config.json` превратил её в опечатку.

**Исправление**: проверять модули в `module_loader_config_correct()` — открывать
файл и убеждаться, что `app_init` экспортируется, не вызывая его. Это ловит
опечатку в пути, недостающий `app_init` и битый `.so`, то есть всё, что является
ошибкой конфигурации. Отказ самого `app_init()` остаётся фатальным, но это уже
ошибка кода приложения, и проявится она на первом же старте.

## 5. Шаги реализации

0. **Сначала — §4**: проверка модулей в `module_loader_config_correct()`.
   Независимый дефект, чинится и проверяется отдельно от всего остального.

1. **Общая функция теневой загрузки** — `core/src/moduleloader/shadowload.{c,h}`:
   `void* shadow_dlopen(const char* path, int flags, const char* tmpdir)`.
   Внутри: проверка `RTLD_NOLOAD`, сравнение `stat`, копирование, `dlopen` копии,
   запоминание пути копии для последующего удаления. Настоящий путь сохраняется
   и подставляется во все сообщения об ошибках вместо пути копии.

2. **Модуль приложения** — `appmodule.c`: перейти на `shadow_dlopen`, перенести
   список модулей из статической переменной в `appconfig_t` (§3.4), освобождать
   его из `appconfig_clear()` рядом с `routeloader_free(taskmanager_loader)`.
   Прочитать `main.tmp` из json-документа в `app_modules_load` и передать дальше.
   Коллбеки контекстов — в `appconfig_t`; обратная ссылка `server_t -> appconfig_t`
   проставляется при разборе `servers`; `httpctx_init()` / `wsctx_init()` получают
   коллбек параметром и хранят его в контексте (три вызова в ядре плюс тесты).

3. **Обработчики** — `routeloader.c`, `routeloader_load_lib()`: тот же переход;
   в `routeloader_lib_t` добавить путь копии — но **не удалять** её в
   `routeloader_free`: файл переживает выгрузку (§3.3). Пути копий собираются в
   процессном списке, который освобождается при выходе. Источник `tmpdir` —
   `config->env.main.tmp`, он заполнен к моменту разбора `servers`.

4. **Удаление копий**: процессный список путей; обход и `unlink` при штатном
   завершении (рядом с `app_modules_free` в `apps/server/main.c`, и в `migrate`),
   плюс уборка чужих остатков при старте — вызов из `module_loader_init` до
   загрузки чего-либо, с пропуском файлов живых процессов.

5. **Тесты** — `core/tests/unit/`: правило совпадения `dlopen` (симлинк, жёсткая
   ссылка, копия), удаление копии после `dlclose`, откат в `tmpdir` при
   read-only каталоге.

6. **Документация** — `hot-reload.md` и `config.md` обеих локалей: раздел
   «Обновление кода без рестарта» переписать (версионированные имена перестают
   быть единственным способом), добавить оговорку про `$ORIGIN` при откате в
   `tmp` и про накопление копий модуля.

## 6. Критерии готовности

* пересобранный на месте обработчик подхватывается по `SIGUSR1`;
* то же для модуля приложения из `main.modules`;
* отчёт ASan для упавшего обработчика содержит имя функции, файл и строку;
* обработчик, зависящий от библиотеки в своём каталоге через `$ORIGIN`,
  загружается после пересборки;
* после **завершения** процесса в каталоге не остаётся `.cwfr-shadow-*`; после
  перезагрузки они, наоборот, на месте — файл переживает выгрузку (§3.3);
* старт удаляет остатки прежних запусков и не трогает копии живых процессов;
* многократная перезагрузка с пересборкой не наращивает RSS и число отображений
  (`/proc/PID/maps`) — старое поколение действительно выгружается;
* перезагрузка с битым путём в `main.modules` отклоняется на этапе проверки, а
  сервер продолжает обслуживать запросы на старой конфигурации;
* перезагрузка с пересобранным модулем, регистрирующим деструктор контекста,
  проходит;
* `ctest` — все наборы; Debug с ASan и `-fanalyzer` — без предупреждений.

## 7. Риски и границы

* **Разбор core dump после перезапуска.** Пока процесс жив, символизируется всё.
  Но старт нового процесса удаляет копии прежнего, так что core упавшего сервера
  надо разбирать до перезапуска — либо сохранить каталог с `.cwfr-shadow-*`
  заранее. Стоит назвать в документации рядом с описанием перезагрузки.
* **Копии копятся на диске** в пределах жизни процесса: файл переживает выгрузку
  библиотеки и удаляется только при выходе (§3.3). Верхняя граница — число
  пересборок за время работы, помноженное на размер `.so`; долгоживущий сервер с
  ежедневным деплоем через `SIGUSR1` наберёт единицы мегабайт в год. Память при
  этом не растёт.
* **Требуется право на запись** в каталог с `.so`. Без него — откат в `tmp` и
  потеря `$ORIGIN` для приватных библиотек рядом с обработчиком. Системные
  библиотеки не затрагиваются.
* **Изменение сигнатуры `httpctx_init()` / `wsctx_init()`.** Функции публичные
  (`protocols/http/httpcontext.h`), но вызываются только ядром — приложение их не
  трогает с тех пор, как они перестали быть его обязанностью. Тем не менее это
  ломающее изменение заголовка, и его стоит отметить в `INSTALL.md`.
* **Гонка при пересборке.** Линкер над существующим файлом делает
  `unlink()`, затем `openat(O_CREAT|O_TRUNC)` и пишет содержимое (проверено
  strace; inode при этом меняется). Отсюда два следствия. Первое — работающий
  сервер защищён: `unlink` отвязывает только имя, а inode с замапленной
  библиотекой живёт, пока есть отображение, поэтому пересборка под работающим
  процессом безопасна и `SIGBUS` не грозит. Второе — окном гонки является **вся
  запись файла**: между `O_TRUNC` и последним байтом по пути лежит новый, но
  неполный ELF, и снятая в этот момент копия окажется усечённой.

  Не опасно: `dlopen` отвергнет такой файл, отказ придётся на фазу проверки (§4),
  и сервер продолжит работать на старой конфигурации. Но перезагрузка тихо не
  сработает, и сигнал придётся повторить. Самоисправляется: при следующей
  перезагрузке `stat` снова отличается от запомненного, и копия снимается уже с
  целого файла.

  Смягчение на стороне деплоя, не фреймворка: слать `SIGUSR1` после завершения
  сборки, либо собирать во временный каталог и публиковать через `rename`,
  который атомарен. Ждать «стабилизации» mtime внутри сервера — эвристика без
  гарантий, делать так не стоит.

## 8. Что вышло, и почему §3.4 не вышло

### 8.1 Сделано

* **§4 — отказ при загрузке модулей больше не убивает сервер.**
  `app_modules_check()` (`appmodule.c`) вызывается из
  `module_loader_config_correct()` после `module_loader_config_load()`: каждый
  ещё не загруженный путь из `main.modules` открывается и проверяется на экспорт

### 8.2 Чего §3.4 не учитывает

Теневая копия модуля приложения не даёт нового поколения кода — она даёт
**смесь двух**.

Обработчик находит модуль по `SONAME`: `libapp.so` в его `DT_NEEDED`.
`_dl_map_object` отвечает на такой запрос первым подходящим объектом из списка
загруженных, а список пополняется с конца. Старый `libapp.so` в нём всегда
раньше новой копии, поэтому обработчики **нового** поколения связываются со
**старым** модулем. Проверено:

```
поколение 1: ver=1 handler()=1
поколение 2: ver=2 handler()=1     ← новый обработчик, старый модуль
```

Отсюда два следствия, и оба хуже нынешнего поведения:

* один запрос нового поколения ходит в обе сборки сразу — middleware и
  деструкторы контекста из новой копии (их адреса регистрирует `app_init()`),
  всё, что вызывает обработчик, — из старой;
* старый модуль больше никогда не выгружается: новые обработчики держат на него
  зависимость. Число отображений растёт на каждую пересборку, что прямо нарушает
  критерий §6 «многократная перезагрузка не наращивает отображения»:

```
после поколения 1        app=1 handler=1
после поколения 2        app=2 handler=2
после гашения 1          app=2 handler=1   ← модуль остался
```

Обойти это нечем. `RTLD_GLOBAL` ищет в том же порядке; `dlmopen` в отдельное
пространство имён разорвал бы общее состояние фреймворка; выгрузить старый
модуль раньше загрузки новых обработчиков нельзя — ради этого он и не
выгружается. Единственный работающий приём — раздать поколениям **разные**
`SONAME`, то есть править `DT_SONAME` в копии модуля и `DT_NEEDED` в копиях
обработчиков (строки одной длины в `.dynstr`), — это правка ELF на пути
перезагрузки, и без отдельного решения её делать не стоит.

Поэтому §3.4 и всё, что из него следует (перенос списка модулей и коллбеков
контекстов в `appconfig_t`, обратная ссылка `server_t -> appconfig_t`, смена
сигнатур `httpctx_init()` / `wsctx_init()`), не реализовано. Модуль приложения
по-прежнему меняется версионированным именем в `main.modules` или рестартом, и
документация теперь объясняет почему.

### 8.3 Чего не было в плане и потребовалось

`module_loader_config_correct()` грузит обработчики **отдельным поколением**,
которое тут же выбрасывает вместе с `dlclose`. При наивной проверке «файл
отличается от запомненного» этот проход съедал признак пересборки: копия
делалась для проверочного поколения, а настоящая загрузка видела уже совпадающий
`stat` и получала от `dlopen` старый объект. Наблюдалось как «копия на диске
есть, а сервер отвечает старым кодом».

Поэтому `shadow_entry_t` помнит не только состояние файла, но и **копию,
сделанную для этого состояния**. Повторная загрузка того же состояния повторяет
решение: `dlopen` той же копии. Это же убирает лишние копии на перезагрузках без
пересборки — два поколения разделяют одну библиотеку, как и предполагал §3.4, — и
даёт расход меньше ожидаемого: копия нужна лишь пока по пути жив старый объект,
а после его выгрузки хватает обычного `dlopen`. Замер на двенадцати пересборках
подряд: одно отображение обработчика в каждый момент, RSS ровный, шесть файлов
копий.
